Preamble — Foundational Design Language

Before the four formal gaps can be resolved, the session surfaced a foundational layer of design vocabulary and actor composition that all gap decisions build on. This section locks that layer.

Section 1 — Vocabulary

These terms are now canonical across all design and implementation discussions.

Term Definition
Phase A discrete step in an actor’s daily routine. Ephemeral — does not survive a save. Owned by BehaviorSchedule.
Routine An ordered sequence of Phases defining a role’s daily cadence. Data, not logic. Externally assigned to a worker by their lord via LordDirective.
Routine Variant A named routine configuration the lord can assign. Initial variants: STANDARD_ROUTINE, DOUBLE_SHIFT_ROUTINE. Routine swaps take effect only at day_tick boundary — never mid-phase.
Interrupt An event_interrupt signal that breaks the current phase mid-cycle. Sourced from the SimClock event queue.
Obligation (Rejected.) Previously considered as a phase injected by an external authority. Superseded by Routine Variants — the lord changes the whole routine, not individual phases.
Headless Event A sim-layer event with no active-layer representation. No signal emitted. Processors handle silently.
Latent Event A sim event that could surface to the active layer. Emits a self-contained payload to the event bus. If nothing is listening, it disappears harmlessly. The sim does not know or care if anyone catches it.
WorkerReport A typed snapshot of a worker’s state at night_tick. Emitted by the worker, received by the lord’s LordLedger.
LordDirective A resource on the worker actor. The lord writes it; the worker’s BehaviorSchedule reads it. Never the reverse.
LordLedger A node component on the lord actor. Accumulates WorkerReport entries: most-recent per worker, plus a rolling 7-night history.
LordPolicyEngine A node component on the lord actor. Reads LordLedger at day_tick, applies AI decision logic, writes updated LordDirective resources to affected workers.

Section 2 — Actor Composition Model

Worker Actor

Actor (Node)
├── EconomicProfile   (Resource)  — grain, coin; saveable, high-read-frequency
├── NeedsState        (Resource)  — hunger, restfulness, morale; drives behavioral decisions
├── ContractState     (Resource)  — employer_id, wage, contract lifecycle state
├── LordDirective     (Resource)  — current routine assignment; lord writes, worker reads
├── BehaviorSchedule  (Node)      — reads LordDirective; advances phase on day_tick signal
└── RoleCapabilities  (Node)
    └── FarmerCapability (Resource) — assigned_plot_id, land_area, crop_type

Key principles: - The actor is a Node that owns components, not a flat struct. - Resources are for durable, serializable, high-frequency-read data. - BehaviorSchedule is a Node because it receives signals, can be paused, and can be replaced when an actor changes role. - Processors receive the actor node and query capabilities — they never switch on a role enum.

Lord Actor

Actor (Node)
├── EconomicProfile   (Resource)
├── NeedsState        (Resource)  — lords have needs too (abstracted in early epics)
├── ContractState     (Resource)  — obligations to higher lords, tax agreements
├── LordLedger        (Node)      — accumulates WorkerReports from all managed workers
└── LordPolicyEngine  (Node)      — reads ledger at day_tick; writes LordDirectives

Section 3 — Morale Model

Rule: Morale is a float in NeedsState. It has one drain source and one recovery source.

Event Morale Effect
Actor completes a WORKING phase Decrements morale by work_morale_cost
Actor completes a SOCIALIZING phase (tavern) Increments morale by social_morale_recovery
RESTING phase No morale effect (restfulness recovery only)

DOUBLE_SHIFT_ROUTINE removes the SOCIALIZING phase. Without recovery, morale drains monotonically until the work incapacity threshold is crossed.

Tuning parameters (not locked — requires playtesting): - work_morale_cost — morale drained per WORKING phase - social_morale_recovery — morale recovered per SOCIALIZING phase - morale_incapacity_threshold — floor below which UNABLE_TO_WORK is set - These values live in the archetype config resource, not hardcoded in processors.

Balance contract: Morale must drain gradually. There is a warning band between “morale feels bad” and the UNABLE_TO_WORK threshold. A lord reading their ledger has at minimum 2–3 nights to intervene before incapacity.

Section 4 — Condition States

Four condition states. These are flags that modify or suspend the routine. They are not phases.

Flag Meaning Upstream Inputs
HUNGRY Food need is unmet Hunger float in NeedsState crosses threshold
BROKE Cannot afford goods at current market prices Coin in EconomicProfile vs. market price
UNABLE_TO_WORK Actor cannot perform labor this tick Terminal output of morale collapse, food failure, or economic squeeze
MARKET_SEEKING Actor is pathfinding to a non-local market Price differential exceeds travel cost (actor has sufficient coin)

HUNGRY and BROKE are inputs to UNABLE_TO_WORK, not synonyms. An actor can be HUNGRY and still work — for a while. When they cross the threshold, UNABLE_TO_WORK is set AND incapacity_cause is written.

STRIKING (prototype name) is retired. UNABLE_TO_WORK replaces it with cause attribution.

Section 5 — Work Incapacity Cause Attribution

UNABLE_TO_WORK alone is not actionable. The lord needs to know why. Each cause requires a different intervention.

enum WorkIncapacityCause {
    NONE,              # actor is capable — no incapacity
    MORALE_COLLAPSE,   # morale drained below work threshold (overwork, no recovery)
    FOOD_ABSENT,       # food not available in market or actor inventory
    FOOD_UNAFFORDABLE, # food exists but price exceeds wages (economic squeeze)
    COMPOUNDING,       # multiple causes simultaneously active
}

Cause → Lord intervention mapping:

Cause Player/Lord Response Problem Type
MORALE_COLLAPSE Change routine (ease schedule, grant rest) Management — internal to lord control
FOOD_ABSENT Supply-side action (trade routes, production) Logistics — external systems
FOOD_UNAFFORDABLE Wage intervention, price caps, merchant pressure Political-economic — adversarial actor
COMPOUNDING Multiple interventions required Systemic failure

Reserved for later scope (architecture must not close the door): - GRIEF_TRAUMA — social cause; requires a human gesture from the lord, not a schedule change - ILLNESS — body failure; lord can mitigate (healers, sanitation) but not prevent outright

Section 6 — Night-Tick Reporting Chain

Flow:

Worker (night_tick fires)
    → emits WorkerReport snapshot
        → LordLedger.receive_report()      [passive accumulation]
            → LordPolicyEngine.evaluate()  [at next day_tick]
                → writes LordDirective     [takes effect at next day_tick boundary]

Separation: There is always a half-cycle gap between worker emission (night_tick) and lord decision (day_tick). Lords are not omniscient. A worker can bottom out their morale and sit there for up to one full night before the lord knows. This is intentional world coherence, not a system flaw.

Population aggregation: LordLedger maintains a nightly_cause_summary — a count of actors per WorkIncapacityCause per night. The LordPolicyEngine reads the summary for systemic signals (e.g., five actors in the same region reporting FOOD_ABSENT on the same night = supply chain failure, not individual bad luck).

Section 7 — Presentation Layer (Hybrid)

The report serves two consumers with different needs:

Consumer What They See Format
LordPolicyEngine (AI) Typed floats, cause enum, condition flags, trend deltas Structured WorkerReport data
Player (as lord) Human-texture narrative dispatches; threshold alerts Editorial filter over the same data

The system captures everything. The player presentation layer filters to signals (threshold crossings, cause attributions, trend alerts) — not raw telemetry. The player should feel like they are reading morning intelligence dispatches, not auditing a spreadsheet.

Dispatch design principle: Signals must be legible in retrospect. After a work incapacity event, the player should be able to look back at the prior three dispatches and say “it was all there.” The dispatches are the tutorial — they teach the player to read the system without tooltips.

func _append_history(report: WorkerReport) -> void:
    if report.actor_id not in report_history:
        report_history[report.actor_id] = []
    var history: Array = report_history[report.actor_id]
    history.append(report)
    if history.size() > HISTORY_DEPTH:
        history.pop_front()

func _update_cause_summary(report: WorkerReport) -> void:
    if report.incapacity_cause == WorkIncapacityCause.Cause.NONE:
        return
    var cause = report.incapacity_cause
    nightly_cause_summary[cause] = nightly_cause_summary.get(cause, 0) + 1

actor.gd (skeleton)

class_name Actor
extends Node

@export var economic_profile: EconomicProfile
@export var needs_state: NeedsState
@export var contract_state: ContractState
@export var lord_directive: LordDirective
@onready var behavior_schedule: BehaviorSchedule = $BehaviorSchedule
@onready var role_capabilities: Node = $RoleCapabilities

func get_capability(capability_class) -> Resource:
    for child in role_capabilities.get_children():
        if child is capability_class:
            return child
    return null

func emit_night_report(tick: int) -> WorkerReport:
    var report := WorkerReport.new()
    report.actor_id = name
    report.tick = tick
    report.morale = needs_state.morale
    report.hunger = needs_state.hunger
    report.restfulness = needs_state.restfulness
    report.coin = economic_profile.coin
    report.routine_id = str(lord_directive.assigned_routine)
    report.incapacity_cause = needs_state.incapacity_cause
    if needs_state.is_hungry:
        report.condition_flags.append("HUNGRY")
    if needs_state.is_broke:
        report.condition_flags.append("BROKE")
    if needs_state.unable_to_work:
        report.condition_flags.append("UNABLE_TO_WORK")
    if needs_state.is_market_seeking:
        report.condition_flags.append("MARKET_SEEKING")
    return report
